Best settings shape: configure the runtime, not arbitrary code inside Pecan.

For Pi extensions, Settings can manage an extension profile: path/package, scope (global/project), enabled state, trust, and restart-required status. Pecan launches stock pi --mode rpc; Pi remains responsible for loading and executing the extension.

  • Show provenance and capabilities before enabling: “runs arbitrary Node code with host access.”
  • Use a test/disable action and surface loader errors from Pi.
  • Separate Pi extensions from Pecan UI plugins; do not load TypeScript Pi extensions into the Rust server or browser.
  • When a runtime cannot support an extension primitive, show a capability report and explicit fallback—not a silent no-op.

Start with initialize, list/read, start/resume, turn events, interrupt, and model listing. Defer rich approvals and mutations until recovery semantics are solid.

Migration order

  1. Parse runtime/native identity; make non-Pi projections read-only.
  2. Finish Pi provider/model capability gating.
  3. Extract current worker into PiAdapter.
  4. Add normalized events + runtime registry.
  5. Add Codex app-server.
  6. Add OpenCode server.

Proof that matters

  • One fixture per runtime produces the same normalized event stream.
  • Fake-process tests for framing, exit, timeout, backpressure, and cancellation.
  • Every blocking interaction is visible, answerable, and cancelled on shutdown.
  • Capabilities disable controls instead of guessing.
  • Projection replacement is atomic and never prunes on an incomplete native scan.
